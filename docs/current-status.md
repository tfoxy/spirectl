  - `cargo test -p sts2`

  - `cargo run -p sts2 -- --json inspect ai-tools`

- Broader automated coverage is summarized in [testing](./testing.md), including Rust CLI snapshots, .NET bridge tests, helper-tool tests, and Node/MCP wrapper tests.

## Documented live/manual flows

- Live lifecycle loop now includes explicit bridge-only install via `sts2 game install-bridge`, full bridge+mod deploy via `sts2 game deploy <mod-project> --build --restart --verify`, separate `sts2 game launch` / `sts2 game attach` flows, plus explicit `sts2 game close` and `sts2 game kill` shutdown controls for later restart orchestration.
- `sts2 game bridge-health` remains the read-only baseline; `--non-mutating` is accepted as a compatibility no-op, explicit stale endpoint cleanup is mode-gated behind `--repair-stale-endpoint`, and `sts2 dev visual-preflight` is the one-shot bridge+lifecycle+artifact preflight for live encounter verification.
- M52-M55 shipped local checkpoint experiments, shareable `dev scenario export|load`, per-field restore support, validation summaries, and multiplayer restore limits. M59 now replaces the active checkpoint command surface with `dev fixture record|resume|status|clear|load`; the replacement records screen-entry fixture recipes instead of promising arbitrary mid-screen runtime resume. M66 extends `dev scenario export --include-exact` with save-backed exact sidecars for supported native run-save continuation, while fixture-backed exact bundles and recorded fixtures still report RNG/runtime omissions honestly.
- Machine-specific STS2 install, assembly, resource, and mods roots should live in ignored local config such as `sts2.local.yaml` copied from `sts2.local.example.yaml`, not committed docs or source files.
- Downstream .NET mods can reference the M75 embeddable runtime facade through `Spirectl.Sts2.Embedding.ISpirectlRuntime`; see [embeddable runtime](./embeddable-runtime.md). This path is in-process and does not require an installed `sts2` binary, automation service, MCP adapter, IPC host, or loopback TCP host.
- S119 names embedded `GetCurrentState(CurrentStateRequest)` as the direct first-load semantic observation path for downstream mods. It returns the current product-neutral state for the requested perspective through the same observation/mapping core used by CLI state views, with structured error/health data when the live host cannot provide state. Embedded `SubscribeCurrentState(CurrentStateSubscriptionRequest, ...)` and `WatchCurrentStateAsync(...)` provide reactive semantic state notifications for other .NET mods: accepted `spirectl` semantic actions schedule coalesced refreshes, live dispatcher ticks provide bounded fallback detection for outside changes, and duplicate fingerprints are suppressed. Those three are the whole embedded state surface — S118's `GetLatestState(EmbeddableLatestStateRequest)` cache and the `GetState` alias were specified and never shipped, so an embedder that wants a last-known snapshot keeps one itself off the subscription (see [known gaps](known-gaps.md)). Current and subscribed semantic state remains separate from presentation rendering, screenshots, asset extraction, browser sessions, routes, cache headers, WebSocket policy, and product DTOs.
- Embeddable runtime now exposes a dedicated in-process asset-provider surface (`runtime.Assets.GetAsset(...)`, `runtime.Assets.GetAssets(...)`) that returns bytes + metadata + structured notices/errors while staying layered over the same bridge runtime extraction path used by extraction workflows. Downstream products remain responsible for URL routing and cache policy.
- No presentation snapshot/render/catalog surface ships any more: the protobuf-backed presentation APIs, the bridge-side layout reload APIs, the `presentation` CLI command group, and the checked-in scene binding catalog are all gone. Downstream renderers consume the live scene-state producers plus semantic state, models, and assets.
- The `@spirectl/presentation` TypeScript package ships two subpaths, not a renderer. `./render` is the shared render vocabulary for mirror hosts: `applyAnimationBinding`, `ensureAnimationStyles`, `PresentationAnimationBinding`, `PresentationAnimationOptions`, `DEFAULT_BBCODE_TAGS`, and `playZoneThreshold`. `./spine` is DOM-free Spine/geoclip clip parsing and frame sampling for a host that owns its own canvas and resource loading.
- S99/S107 expanded embeddable asset-provider representative combat coverage across model-backed card/relic/potion/character assets, direct `res://` UI/status/VFX resources, composed combat backgrounds, and composed encounter render targets. Unsupported or malformed untyped status, UI, VFX, enemy, and encounter keys return structured diagnostics such as `invalid-asset-key`, `asset-key-not-found`, or `unsupported-asset-kind`; `composed://encounters/<id>/scene-package` metadata payloads preserve structured package notices in `payload.notices`.
- The runtime state contract now includes presentation-grade combat data for UI consumers: player gold/relics/potions/piles/status effects, card descriptions and generic asset keys, enemy status/intent/visual metadata, run breadcrumbs, screen source metadata, and structured notice `path` / `severity` / `source` fields. Default `state` remains the semantic source of truth for observed values and action availability; assets/action execution remain separate surfaces. These fields are generic and additive, not CouchCoop-specific DTOs or asset URLs.
- `usageTracking.enabled: true` enables local command tracking under `usageTracking.dir` (default `./.sts2`) with append-only `cli-history.txt` and aggregate `cli-stats.csv`; it records canonical top-level command paths only and omits all arguments.
- `sts2 game launch` now repairs a missing, invalid, stale, or incomplete deployed bridge payload before it starts the game, supports optional `game.launchWrapper` prefixes such as `xvfb-run -a`, prefers the native Linux `SlayTheSpire2` launcher name before `.x86_64` fallbacks, detaches the launched process into a new Unix session by default with `--no-detach-session` as an explicit opt-out, and returns structured `launch_executable_not_found`, `launch_executable_ambiguous`, `launch_timeout`, or `launch_exited_before_ipc` failures with `configKey: game.launchExecutable` guidance instead of leaking `game attach` timeout metadata.
- `sts2 game deploy --restart` now surfaces `configKey: game.stopCommand` guidance on platforms that require an explicit stop command rather than silently failing when automatic restart cannot stop the running game safely.
- `sts2 game close` now performs bounded graceful shutdown through bridge close, configured `game.stopCommand`, or exact Linux `SIGTERM` matching; `sts2 game kill` is an explicit force path using exact Linux `SIGKILL` matching and never runs the configured stop command.
- Direct live transport failures from `game attach`, `state`, `act`, and `dev *` now distinguish Unix-socket bootstrap/socket errors, local transport misconfiguration, and local endpoint connection failures across Unix IPC and TCP paths.
- `sts2 game install-bridge` and `sts2 game deploy` now stage the published standalone bridge payload directly from the host project output without requiring a matching local `Microsoft.AspNetCore.App` shared runtime.

## Partial capabilities

- `sts2 act play-card` now executes through the live bridge for currently legal hand cards and targets.
- `sts2 act use-potion` now executes through the live bridge for currently usable combat potions, including legality-checked target selection when the potion requires a combat target.
- `sts2 act choose` now executes through the live bridge for `menu:start-run` when the active main-menu screen resolves a callable start-run hook from the ordered screen-method, known button-member, and live tree probe path inspection, plus visible reward buttons, visible event-room options, the enabled map back flow as `map:back`, the pre-open Fake Merchant `event-room:fake-merchant:open-shop` entry, Crystal Sphere Big/Small Divination, hidden-cell, and enabled proceed choices, visible treasure-room chest/relic/proceed choices, visible `relic-selection` overlays through the same treasure-room hooks, visible rest-site options, visible shop merchant slots plus normal-shop `shop:leave` and Fake Merchant `shop:close-inventory` flow buttons, visible card-selection card picks, generic card-selection skip buttons, card-reward alternative buttons, visible `bundle-selection` bundle-row choices through the same card-selection hooks, the enabled reward proceed/skip button on the rewards screen, and the enabled rest-site proceed button in the active room.
- Custom event controls remain intentionally narrow rather than generic UI automation: pre-open Fake Merchant exposes only `event-room:fake-merchant:open-shop`, opened Fake Merchant inventory remains the existing `shop` surface with `shop:close-inventory` for the embedded inventory close button, and Crystal Sphere exposes only Big/Small Divination, hidden coordinate cells, and enabled proceed.
- `sts2 act confirm-selection` and `sts2 act cancel-selection` now execute staged card-grid follow-through on `simple-card-selection` and `deck-card-selection` overlays. Simple selection confirm completes the staged pick and cancel clears staged picks, while deck selection confirm drives the preview-to-confirm flow and cancel either backs out of preview or clears staged picks before preview.
- Live `main-menu` state keeps `choices: [menu:start-run]` as the visible-choice surface, but `availableActions` now advertises `action:menu:start-run` only after the bridge verifies a callable Start Run hook; otherwise state adds `main-menu-start-run-hook-unavailable`, and forced execution failures report `resolved_hook_path`, `checked_probe_paths`, and `present_candidates`.
- The checked-in smoke scenarios are now split deliberately: `tests/scenarios/smoke-main-menu.sts2.yaml` stays as the lightweight mock baseline, while `tests/scenarios/smoke-main-menu-live.sts2.yaml` is the explicit live validation path that waits for executable `availableActions` before choosing Start Run and then expects `Screens.CharacterSelect.NCharacterSelectScreen`.
- `sts2 act select-map-node` now executes through the live bridge for currently travelable map nodes, and the same map screen exposes node choices plus executable `select-map-node` actions and an enabled back button as `choose --choice map:back`.
- Open map state takes precedence over retained room, combat, event, reward, treasure, or overlay screen references, so `state` follows the visible map and exposes map choices/actions after opening the map from another flow.
- Player-scoped visible choices now carry additive `ownerPlayerId` in `state.choices[]` on map, rewards, event-room, treasure-room, rest-site, shop, and card-selection screens, so scripts can attribute visible-but-not-yet-executable choices without inferring from `availableActions[]`.
- Combat target choices now also carry additive `ownerPlayerId`, so visible target markers point back to the active acting player the same way combat `availableActions[]` already do.
- Map, rewards, event-room, treasure-room, rest-site, shop, and card-selection state now add family-specific partial notices when a visible choice is intentionally not executable yet, instead of silently leaving callers to infer that gap from `choices[]` / `availableActions[]` alone.
- S85 now ships the breaking current action/choice contract on top of the S83/S84 typed state sections: `map.nodes[]`, `eventRoom.options[]`, `treasureRoom.relics[]`, `relicSelection.relics[]`, `restSite.controls[]`, `shop.purchasableItems[]`, `rewards.rewards[]`, `cardSelection.cards[]`, `simpleCardSelection.choices[]`, `deckCardSelection.deckCards[]`, `bundleSelection.bundles[]`, `lobby.players[]` / `actions[]`, and observable `cardOverlay` detail/breadcrumb/fallback metadata are the preferred read surfaces.
