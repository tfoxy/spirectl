## Supported now

- Live screen classification and state extraction exist for `main-menu`, `combat`, `map`, `event-room`, `crystal-sphere`, `treasure-room`, `relic-selection`, `rest-site`, `card-selection`, `simple-card-selection`, `deck-card-selection`, `bundle-selection`, `shop`, `rewards`, `Screens.CharacterSelect.NCharacterSelectScreen`, and `Screens.CharacterSelect.NMultiplayerLoadGameScreen`.
- Supported live screen ids are now normalized through shared active-screen and overlay-family resolvers, so derived/modded subclasses of the shipped `card-selection`, lobby, reward, shop, room, and main-menu screen classes continue to route into the same observation paths instead of silently downgrading to unsupported or falling back to generic combat overlay handling.
- Main-menu state keeps the visible `menu:start-run` choice provisional, and only advertises `action:menu:start-run` after the live bridge verifies a callable Start Run hook on the active screen object through the same ordered screen/button/tree probe result used by `act choose`.
- Combat state includes perspective-aware hand/player filtering through `RuntimeStateMapper`.
- Combat state now also includes perspective-aware potion visibility for the active player belt plus per-player potion lists in multiplayer-aware combat payloads.
- Combat and run state now include presentation-grade additive fields for UI consumers: card `description` / `type` / `rarity` / `targetType` / `costLabel` / `assetRefs`, player `gold` / `relics` / `potions` / `masterDeck` / `statusEffects`, combat `drawPile` / `discardPile` / `exhaustPile`, enemy `runtimeEntityId` / `modelId` / `statusEffects` / `visual` / intent labels and targets, and run/screen breadcrumbs such as `actLabel`, `floorLabel`, `encounterId`, `encounterLabel`, `roomLabel`, `screen.source`, `screen.rawType`, and `screen.className`.
- Cataloged special encounters can expose provisional shared `combat.encounterVisuals`. Kaiser Crab currently reports `packageId`, `encounterId`, `visualParts[]` with `partId`, logical `actorId`, `activeStateId`, `screenSide`, and `anatomicalSide`, bounded `recentEvents[]`, and notices. The section is shared across multiplayer perspectives and is not filtered out for local perspective because it represents encounter-owned visuals rather than hidden player-owned data.
- Presentation asset references are typed model keys, composed keys, or direct `res://...` resources such as `model://cards/<model-id>/image`, `model://relics/<model-id>/icon`, `model://potions/<model-id>/icon`, `model://monsters/<model-id>/visuals`, `model://events/<model-id>/backgroundScene`, `res://resources/textures/icons/status_weak.png`, and `composed://combat-background/<id>/image`; they are not downstream URLs or layout decisions.
- Default state remains semantic and action-oriented. Layout, viewport metadata, and explicit-player render payloads belong to a downstream renderer, not to default `GetCurrentState`.
- Local perspective filtering keeps remote run/combat identity and HP summaries but removes remote-owned presentation lists/pile details when they are not observable, adding `player-presentation-filtered` only when data was actually removed.
- Lobby, run, and combat sections include by-id maps for script and AI stability.
- Multiplayer lobby players now resolve display names from platform metadata, expose additive `isLocal` / `isHost` / `isRemote` role flags, and `hostPlayerId` now resolves from host/client net-service metadata when the underlying runtime exposes it.
- Run and combat players now also expose additive `isLocal` / `isHost` / `isRemote` role flags, so multiplayer identity survives beyond the lobby screen and into active gameplay slices.
- Load-run lobbies now preserve the loaded save summary through the existing `run` envelope (`seed`, `floor`, `act`, and by-id player summaries) when `LoadRunLobby.Run` is available.
- Event rooms expose typed `eventRoom.page` for the currently visible localized rich event title/body/shared label, plus `eventRoom.options[]` for visible event options and option descriptions. Event text is read from live `LocString.GetFormattedText()` when available so the active game language and tags such as `[red]` / `[wave]` are preserved; layout-label fallback emits notices. Ancient events are still event-room layouts, not reward screens: their title/banner/epithet/current dialogue are under `eventRoom.page.ancient`, and relic rows remain in `eventRoom.options[]`. The typed `eventRoom` section is the public read for this surface when callers need event text.
- Pre-open Fake Merchant exposes exactly one `event-room:fake-merchant:open-shop` choice while the merchant button is visible; opened Fake Merchant inventory is covered by the existing shop family when the active screen resolves as `screen:shop:NFakeMerchantInventory`, and its purchase choices plus `shop:close-inventory` remain `shop:*` choices rather than event-room choices.
- Treasure rooms and `relic-selection` overlays now expose typed `treasureRoom.relics[]` / `relicSelection.relics[]`, keep stable current-screen compatibility choice ids for visible chest/relic/proceed flow, and include executable `availableActions` through the same legality-backed treasure-room hooks.
- Rest-site rooms now expose typed `restSite.controls[]`, keep stable current-room compatibility choice ids for visible options and the enabled proceed button, and include executable `availableActions`.
- Shop screens now expose typed `shop.purchasableItems[]`, keep stable compatibility choice ids for visible cards/relics/potions/card-removal/leave controls, and include executable purchase or flow actions only when legal.
- Reward screens now expose typed `rewards.rewards[]`, keep stable compatibility choice ids for visible rewards and proceed/skip flow, and include executable `availableActions` only for enabled reward controls.
- Card-selection overlays expose typed `cardSelection.cards[]`, keep stable current-screen compatibility choice ids for visible cards, skip buttons, and reward-alternative buttons, and include executable `availableActions`.
- `simple-card-selection` and `deck-card-selection` overlays now expose typed `simpleCardSelection.choices[]` / `deckCardSelection.deckCards[]`, keep stable current-screen card ids as executable `select-card` actions, keep family-specific notices when visible cards remain non-executable, and add follow-through `confirm-selection` / `cancel-selection` actions only when the current staged-selection state makes them legal.
- `run.players[].overlays[]` carries the typed card-choice overlays — `chooseACard` (NChooseACardSelectionScreen), `deckCardSelection` (NDeck*SelectScreen), `simpleGridCardSelection` (NSimpleCardSelectScreen, e.g. Headbutt: `{ promptText, promptLoc, minSelect, maxSelect, canConfirm, canCancel, previewActive, selectedCardIds, cards[] }`), and `bundleCardSelection` (NChooseABundleSelectionScreen, e.g. ScrollBoxes: `{ bundles[] (each `{ id, cards[] }`), canConfirm, previewActive, selectedBundleId }`). The simple-grid and bundle overlays are local-seat-only (game-initiated, inspection-resolved); card ids are the same `card-selection:card:<MODEL>:<index>` select-card ids and bundle ids the `card-selection:bundle:<stable>:<index>` select-bundle ids, so `select-card` / `confirm-selection` / `cancel-selection` / `select-bundle` drive directly off the typed fields.
- `card-overlay` now exposes typed partial `cardOverlay` detail state when observable. The section can include visible card/detail payloads, source-screen breadcrumbs, `overlayPolicy`, close/back compatibility metadata when a legal hook is validated, fallback visible controls, and structured notices for partial, passive, unsupported, or ambiguous ownership cases.
- Overlay precedence is explicit: blocking overlays take precedence in default state, passive card detail overlays retain the actionable underlying screen while adding `cardOverlay`, and unsupported named overlays emit notices instead of fabricating choices or leaking scene-tree internals.
- `crystal-sphere` overlays expose stable visible Big/Small Divination controls, hidden cell controls shaped as `crystal-sphere:cell:<x>:<y>`, and enabled finished proceed flow through S86 event-room verbs; `bundle-selection` overlays now expose typed `bundleSelection.bundles[]`, stable visible bundle ids when the bundle row is visible, and executable `select-bundle` actions.
- Map state exposes typed `map.nodes[]`, visible map nodes as `map-node:<row>:<col>` compatibility choices, currently travelable nodes as `select-map-node`, and the enabled map back button as `back-from-map`.
- `run.map.points[]` additionally carries `revealedRoomType`: for a VISITED `Unknown` (`?`) node, the resolved room type behind it (the game reveals a `?` node's category once travelled), read from the run's map-point history. Empty for non-`Unknown` points, an un-travelled `?`, or when no history row is recorded. Map fixtures author this through `run.currentRoom.mapRoom.travelPath` (a per-row list of `MapPointType` names or `Unknown:<RoomType>` entries) and choose the starting node via `run.currentRoom.mapRoom.firstNode` (`combat` for a Monster first node, `ancient` for the Neow node).
- When the runtime map screen is open, map state takes precedence over retained room, combat, event, reward, treasure, or overlay screen references so `state` reflects the visible map rather than the screen that opened it.
- Player-scoped visible choices on `map`, `rewards`, `event-room`, `treasure-room`, `rest-site`, `shop`, and `card-selection` now include additive `ownerPlayerId`, so downstream callers can attribute the visible choice owner even when the choice is provisional or not yet executable.
- Combat target markers now also include additive `ownerPlayerId`, pointing at the current acting player so visible target choices and executable combat actions expose the same ownership metadata.
- S87 completes the public multiplayer ownership pass for the S83-S86 state/action surface: player-scoped payloads and visible controls use stable `playerId` / `ownerPlayerId` values plus additive `isLocal`, `isHost`, `isRemote`, `hostPlayerId`, `localPlayerId`, `localPlayerRole`, `perspective`, and remote-orchestration capability metadata where the runtime can resolve them. These fields describe ownership and orchestration capability separately from current action legality.
- S108 regression coverage now includes host-local lobby seats in deterministic runner fixtures: host-owned local seats expose `ownerRole: host-local-seat` plus `remoteOrchestration.state: host-local-seat` on typed lobby players and action refs, while true remote players remain visible as remote/local-only-degraded rather than actionable host-local seats.
- Loaded multi-player combat fixtures preserve the same host-local ownership boundary: explicitly authored host-local seats stay visible in `combat.players[]` / `playersById` with local ownership metadata, while true remote players remain non-actionable unless configured ownership exists.
- Perspective filtering is explicit. `local` perspective keeps observable remote identity/summary data but filters remote-owned private presentation/control details, `host` and configured-client perspectives can expose only the player scope actually owned or mediated by the attached bridge/client, and `omniscient` remains a dev/validation perspective rather than normal player observation. When data is hidden or unavailable, the bridge should emit structured notices instead of silently implying that a field does not exist.
- Remote orchestration capability is reported as state/action metadata rather than inferred from `isRemote`: possible meanings are unavailable, local-only degraded, host-mediated, explicitly configured client, or unsupported. A single local bridge must not claim independent control of remote clients that do not have an explicit configured bridge/client.
- Map, rewards, event-room, treasure-room, rest-site, shop, and card-selection screens now emit family-specific partial notices when visible `choices[]` outnumber executable `availableActions[]`, so callers do not have to infer that supported-but-not-executable split from array shapes alone.
- S85/S86 current metadata normalizes typed choice fields and compatibility metadata: `id`, `choiceKind`, `intentKind`, `label`, `description`, `ownerPlayerId`, `perspective`, `arguments`, `enabled`, `disabledReason`, and optional `preferredAction` where the bridge knows the first-party modeled action. S86 modeled controls should point at typed intent verbs for reward/card, shop, rest-site, treasure/relic, map, and event-room groups rather than generic `choose`. Notices should use `path`, `severity`, `source`, `stability`, and `perspective` rather than implying that omitted observable fields are hidden internals.
- `inspect actions` exposes the same public contract as `stateContract`, naming the typed screen and overlay sections, compatibility metadata fields, structured overlay notice fields, passive/blocking precedence policy, fallback `choose` limits, and the dev-only home for raw runtime scene-tree debugging.
- The same observed state and mapper feed `state`, `state screen`, `state actions`, `inspect actions`, CLI-local `dev wait-for`, CLI-local `dev assert`, the CLI-local scenario runner, and the M75/S119 in-process `ISpirectlRuntime.GetCurrentState` facade. The shared core is `ObservedGameStateExtractor` plus `RuntimeStateMapper`; CLI compact JSON is a client projection over that shared current state.
- S119 names `ISpirectlRuntime.GetCurrentState(CurrentStateRequest)` as the direct embedded current-observation API. It returns the current perspective-aware semantic `GameStateSnapshot` through the normal observation/mapping path and structured error/health data when the live host cannot provide state. It is the only synchronous read; the `GetState` alias named by earlier specs was never shipped. Embedded .NET consumers that need reactive changes use `SubscribeCurrentState(CurrentStateSubscriptionRequest, ...)` for callbacks or `WatchCurrentStateAsync(...)` for async streams; both emit `CurrentStateWatchEvent` snapshots with semantic fingerprints/revisions, schedule refreshes after accepted embedded actions, and use live dispatcher ticks as a bounded fallback for changes that happen outside `spirectl`.
- S120 adds `sts2 --json state watch` as the read-only CLI/automation wrapper over the same S119 current observation path. The output is newline-delimited JSON with `initial`, `changed`, and `error` event types; each event includes `sequence`, `observedAtUtc`, a semantic `fingerprint` for state events, and either the selected `state` projection or structured `error` payload. Live IPC/TCP bridges that advertise `state-watch` use the reactive bridge stream by default; older bridges and `--watch-mode poll` use the compatibility polling loop. Use `--max-events`, `--timeout-ms`, `--poll-interval-ms`, `--rpc-timeout-ms`, and `--watch-mode` to bound scripts and tests. Repeated identical semantic states are suppressed until a later changed state or timeout, and state errors are preserved as events unless `--fail-fast` is set. Watch is not CouchCoop, browser startup/session semantics, WebSocket envelopes, latest-state cache freshness, presentation rendering, screenshots, logs, debugger streams, raw scene-tree inspection, or an action-execution surface.
- S118 specified a cache-backed `ISpirectlRuntime.GetLatestState` beside it — latest usable snapshot plus status, revision, age, freshness threshold, refresh-in-progress and health diagnostics — and it was never implemented. Nothing on the interface serves a cached read today; see [known gaps](../known-gaps.md). Presentation rendering, screenshots, and asset extraction stay on the screenshot and asset-provider surfaces.
- CLI `sts2 state` now projects the bridge-native envelope into compact state by default: top-level `language` identifies the active localization used for resolved state strings, `actions[]` replaces default `choices[]` / `availableActions[]`, non-combat and overlay sections normalize under `scene`, and `decision` summarizes the current phase/action surface. `state full` preserves the expanded bridge-native payload for migration/debugging, `state screen` returns bounded classification, `state actions` returns the compact action/ref subset, `state refs` returns a de-duplicated model/asset reference index for downstream caches, and `inspect state-schema` documents the public break.
- Experimental `state` now includes a nullable generic `run` payload whenever the attached runtime exposes an active `RunManager` run. The payload keeps runtime-only facts from `RunState`, `RunManager.NetService`, `Player`, `Creature`, `CardPile`, `RelicModel`, and `ActMap`; model/localized names, text, and assets remain in `models`.
- `state` exposes presentation scene composition instead of a flat screen id. `rootScene` is the current child of `Game.RootSceneContainer`, active runs use `rootScene: "run"`, and `run.currentRoom.scene` names the current child of `Run.RoomContainer` with normalized scene ids such as `rooms/combat_room`, `rooms/event_room`, `rooms/treasure_room`, `rooms/merchant_room`, `rooms/rest_site_room`, and `rooms/map_room`. Event-room nested scene identity is nullable at `run.currentRoom.event.scene` until the live runtime exposes the `EventContainer` child scene reliably. `state` view objects are attached-client local UI state, not remote-player UI state.
- Active combat rooms additionally expose runtime-only `run.currentRoom.combat` data from `CombatRoom` / `CombatState`, while player-owned `PlayerCombatState` data lives under the canonical `run.players[]` entries. `run.players[].creature.currentHp` and `maxHp` are read from persistent `Player.Creature` in every run room; combat-contextual creature fields such as block, hittability, powers, and — for monsters — `nextMove` are populated only for active combat creatures. `nextMove` is `{ id, intents[] }`, where each intent has a `type` (`AbstractIntent.IntentType`) and attack intents add `attack { damage, hits }` (local-perspective single-hit damage; hits = repeats + 1).
- Combat state ids are game-native and identical to the ids the action executor accepts: every creature is `creature:{Creature.CombatId}`, every hand/pile card `id` is the `NetCombatCardDb` id (decimal string), and potions are addressed by slot index. The previously separate `combatId` and `isStunned` creature fields were removed (`id` encodes the combat id; stun is derivable as `nextMove.id == 'STUNNED'`). Combat hand cards add runtime `energyCost` (modifier-applied), `starCost` (`-1` when not star-costed), and `unplayableReason` (the set `UnplayableReason` flag names, null/empty when playable); the legacy `ownerPlayerId`/`currentStarCost` card fields were removed. `run.players[].potions[]` lists every slot in order as `{ id (slot index), modelId (null when empty), isQueued, passesUsabilityCheck }`, replacing the flat `potionSlotModelIds` and omitting target/usability conveniences that are derivable from potion models plus combat state. Potion popup/targeting UI is local view state under nullable `run.view.selectedPotion` (`{ mode: popup|targeting, slotIndex }`). In-hand card selection mode (a card effect asking for hand cards, e.g. Survivor's discard) is local view state under nullable `run.view.handSelection` (`{ playerId, mode: simple-select|upgrade-select, promptText, promptLoc, minSelect, maxSelect, requireManualConfirmation, canConfirm, selectedCardIds, selectableCardIds, sourceCardId, sourceModelId, isPeeking, previewCard }`); card ids match `run.players[].combat.hand.cards` (selected cards stay in the hand pile while staged), and `run.view.isInCardSelection` stays the broader boolean (hand mode OR an `ICardSelector` overlay on the stack). In `upgrade-select` mode (e.g. Armaments) `previewCard` is the upgraded snapshot of the focused card (clone + `UpgradeInternal`, `upgradeLevel` bumped) so the before/after preview renders; it is null in `simple-select` mode or when no card is focused. Raw blockers needed for deriving potion actions are `run.players[].canRemovePotions`, `run.currentRoom.combat.combatState.playerActionsDisabled`, and `run.view.isInCardSelection`. `combatState` keeps `enemies` and `escapedCreatureIds`; the duplicated `playerIds`/`allyCreatureIds`/`enemyCreatureIds` lists were removed as derivable (players = creatures with a `Player`). enemy creatures remain full room-owned payloads, and pet creature state remains under the owning player.
- `state` current-room coverage also includes runtime-only `run.currentRoom.id`, `treasure`, `shop`, `restSite`, and `mapRoom` sections for `AbstractRoom.Id`, `TreasureRoomRelicSynchronizer`, `MerchantRoom.Inventory`, `RestSiteSynchronizer`, and `MapRoom` presence. `run.map.view.isOpen` reflects the attached client's `NMapScreen.Instance.IsOpen` and is independent from the forced `run.currentRoom.mapRoom` section; `run.currentRoom.shop.view.isOpen` reflects `NMerchantInventory.IsOpen`. Treasure votes mirror the game `PlayerVote` shape with nullable `index` plus `voteReceived`, so skipped relics and missing votes remain distinguishable. These sections avoid derived convenience fields such as affordability and omit localized/model/static presentation data.

## Current limits

- Main-menu `choices` and `availableActions` are intentionally not identical: the visible Start Run choice can remain present while `availableActions` omits it and emits `main-menu-start-run-hook-unavailable` when no callable hook is discoverable on the checked probe paths.
- Other supported live screens can also keep `choices` broader than `availableActions` on purpose. Map, rewards, event-room, treasure-room, rest-site, shop, and card-selection emit family-specific notices when some visible choices are still non-executable. S85/S86 shipped the current cleanup where typed choices carry intent metadata and modeled first-party controls point to preferred intent actions, leaving generic fallback choose only for generic, modded, or unmodeled visible choices.
- Start-run and load-run lobby observation now also emits visible local lobby `choices[]` for ready/unready flow plus visible local character-selection rows when the live screen exposes real character buttons, keeping lobby ownership on the same stable-choice surface as the other supported player-scoped screens.
- Card detail overlays are still partial: `cardOverlay` can expose observable detail data and close/fallback metadata, but unsupported or ambiguous overlay controls stay notices or disabled fallback metadata until the bridge can validate legal hooks.
- Unsupported screens still fall back to notices rather than richer extraction, while `simple-card-selection` / `deck-card-selection` expose staged card-grid state plus confirm/cancel follow-through, `bundle-selection` exposes supported bundle-row state/actions, `crystal-sphere` covers only the known custom event controls, and `relic-selection` routes through the supported treasure-room family.
- Lobby player names still fall back to `null` with notices when platform metadata lookups fail.
- Load-run lobbies now expose visible character availability and executable `select-character` actions when discoverable character buttons are present on the active screen.
- Runtime scene tree data is not part of the default `state` surface; live runtime scene observation ships separately through `dev scene tree`, `dev scene node`, `dev scene children`, and `dev scene set-visible`. `dev scene node` is compact by default and exposes property/transform details only when `--properties` and/or `--computed-transform` are requested, including render-relevant diagnostics needed by presentation work. Text-bearing label properties from MegaLabel or MegaRichTextLabel are developer scene diagnostics for targeted investigation and must not be promoted into default observable state.
- Rendering is separate from default semantic state and is not shipped from this repo; a renderer consumes `state`, live scene state, models, and assets.
- Live extraction depends on reflection-heavy hooks in the STS2 host adapter.
- M76 presentation fields are additive and best-effort. Some text/counters/status lists depend on what the current live STS2 objects expose; missing presentation detail should be interpreted through `state.notices[]` with `path`, `severity`, and `source` rather than by treating empty arrays as hidden support.
- `combat.encounterVisuals` is provisional and base-game catalog backed. Non-cataloged encounters omit the section rather than fabricating visual parts; Kaiser transition events are observational Harmony postfixes over known visual methods and are capped to a bounded recent-event list.
- Out-of-combat screens now target S83 typed presentation sections as the default contract. `choices[]` and `availableActions[]` remain compatibility/fallback surfaces, with notices and perspective metadata explaining limitations. Default state remains observable-first; raw runtime scene-tree data belongs in `dev scene tree` / `dev scene node` / `dev scene children`, not in `state`.
- Layout and linkage metadata are not part of default semantic state; missing semantic state or action legality is a state-contract concern and should be reported through `state.notices[]`.
- There is no latest-state cache. The S118 design (a `GetLatestState` returning `Refreshing` / `TimedOut` / `Unhealthy` off a shared cache) was specified and never implemented, and the surface it described does not exist on `ISpirectlRuntime` — see [known gaps](../known-gaps.md). An embedder that wants a last-known snapshot keeps one itself from `SubscribeCurrentState`. If a cache is ever built, its entries have to be scoped by the semantic projection inputs (requested player/perspective, debug inclusion, included sections), because serving one player's private projection as another player's state is the failure mode that makes a naive cache wrong rather than merely stale.
- Current observation is semantic-only. Do not mix browser sessions, routes, cache headers, WebSocket retry policy, rendering, screenshots, asset extraction, or product DTOs into `GetCurrentState` or default `state`.
- State resource references are cache hints over the semantic state. They should point downstream consumers to `GetModels` and the asset-provider surfaces, not become a browser WebSocket envelope or a second full state contract. Embedded consumers can call `StateResourceReferenceCollector.Collect(GameStateSnapshot)` directly.
- The embedded state surface is embedded-only unless a later spec adds a broader transport contract. Do not document or expose it as `sts2 state`, gRPC, IPC, TCP, MCP, screenshot, asset, browser-session, route/cache, or WebSocket behavior.
- Remote-client state and action orchestration beyond explicitly configured clients remains out of scope. Local-only degraded restore can reproduce a reviewable local approximation, but it must continue to report remote-owned players as degraded or omitted through `multiplayerRestore` and field-level restore validation rather than presenting them as controllable clients.

## Scene-stream contracts published to embedders

The live scene delta stream (`SubscribeRuntimeSceneDelta`, produced by
`bridge-mod/src/Spirectl.Sts2/Live/Sts2RuntimeSceneWatcher.cs`) is consumed by embedders that re-project it, so two
parts of it are published as referenceable API rather than left to be copied by hand:

- `bridge-mod/src/Spirectl.Sts2/Core/SceneInspection/RuntimeSceneNodeDeltaFields.cs` — `StaticFieldNames` and
  `VolatileFieldNames` partition `RuntimeSceneNodeDelta`. Static fields ride add/keyframe deltas only; a consumer
  must retain the last non-default value it saw for each and ignore the record default in between. Volatile fields
  are on every emitted delta. The split is defined by exactly one thing — whether the watcher gates that argument
  on its `includeStatic` flag — and `RuntimeSceneNodeDeltaFieldsTests` holds the lists to the record and to the
  watcher's source, so a field added without being classified fails the bridge test leg.
- `bridge-mod/src/Spirectl.Sts2/Core/SceneInspection/SpirectlSceneStreamMeta.cs` — `StreamSkipMetaKey` is the Godot
  metadata key (`spirectl_stream_skip`) an embedder stamps on the ROOT of a subtree that must never reach mirror
  clients, e.g. host-local chrome it injected into the live tree:

  ```csharp
  node.SetMeta(SpirectlSceneStreamMeta.StreamSkipMetaKey, true); // before AddChild
  ```

  Presence is the whole signal; the value is never read, the stamp covers the entire subtree, and removing the meta
  restores streaming. It is honoured by the streaming watcher only, deliberately not by the dev `scene tree` /
  `scene node` inspection surface, so injected UI stays testable from the CLI.
